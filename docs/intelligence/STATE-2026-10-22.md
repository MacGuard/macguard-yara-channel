# Phase 0: the real state of the repository (2026-10-22)

*Resumen: el canal YARA existente es operativo y firmado, pero valida con YARA clásico (no YARA-X). Hay trabajo importante sin integrar en `main` (9 PR en borrador y 4 ramas de agentes). Las 447 pruebas previas pasan, con 1 omisión conocida.*

## What exists on `main` (89162af plus bot commits)

* **The YARA channel** (operational): daily collection from two public rule repositories, static and dynamic gates, decision gate, Sigstore keyless signing, transparency log, signed releases, an independent verifier (`scripts/verify_public_release.py`). Latest release read on 2026-10-22: `rules-20261021-39541028283`, 1178 files, 10,021 rules; `mgctl evidence verify --latest` returned PASS.
* **YARA-X is not part of the pipeline.** `config/sources.json` lists `yara-x` only as `kind: engine` with no paths, and the published manifests say `validation.engine: yara` (classic YARA 4.5.x via `yarac`). There is no YARA-X gate today. "Channel 1: YARA-X" in the new architecture is therefore a *new gate on top of the existing channel*, not something already running (see `VALIDATION-PLAN.md`).
* A review panel/service (Worker + D1), the Installer Auditor app and CLI (`macguard-audit`, macOS only), a static web (`web/`) and a documentation site (`docs-src/`).

## Findings that change the plan

1. YARA-X is not implemented (above): the first channel must be described as classic YARA plus a *planned* YARA-X compatibility gate.
2. The unauthenticated bulk exports of abuse.ch return HTTP 410 (read 2026-10-22); a real IOC source needs an account or key, which this work does not create or use. Real IOC ingestion is therefore blocked, not merely unimplemented.
3. Redistribution of third-party rules is `pending-legal`, and releases ship no licence notices today (see `LICENSE-MATRIX.md` and `THIRD-PARTY-NOTICES-DRAFT.md` on the wiki branch).
4. GitHub/SLSA attestations are not produced; "attestation of tests" is a design (`VALIDATION-PLAN.md`).
