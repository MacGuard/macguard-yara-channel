# Backup authentication and recovery after losing the Mac (2026-10-25)

Status: **designed and tested with throw-away keys (LOCAL_VERIFIED). No real key was created or read, no real backup was signed, nothing was sent to a provider.** Code: `gateway/tools/backup_anchor.mjs`, `recover_verify.sh`, `backup_kit.mjs`, and the `drill --trust-key` and `heads` commands of `backup_objstore.mjs`. Tests: `gateway/test/backup_anchor.test.js` (10), `backup_recovery.test.js` (3), `objstore.test.js` (11); the complete gateway suite is 240/240 at `8f16459`.

## The problem it closes
The checksums, the manifest and the ciphertext of a backup are in the same bucket, and age encrypts to a **public** key. Whoever can write to a bucket can upload a different, perfectly self-consistent backup; a restore drill that only trusts what the bucket says passes it. A local `SHA256SUMS` helps only while the Mac exists. After losing the Mac, nothing independent remained.

## The design
* **A signed statement per backup** (`ANCHOR.json` + `ANCHOR.json.sig`) uploaded with the other three files. It pins the SHA-256 of `d1-export.sql.age`, `manifest.json` and `SHA256SUMS`, the stamp, a **sequence number** (1, 2, 3, …) and the hash of the **previous statement** (a chain).
* **Signer:** an ed25519 SSH key (`ssh-keygen -Y sign`, namespace `macguard-backup/1`). Verifying needs only the **public** key line. No new dependency.
* **Trust anchor = the public key plus the newest sequence you know**, kept in the recovery kit, **outside the buckets and not only on the Mac**.
* What each part defeats: a forged backup (the attacker cannot sign), an altered file (hash mismatch), a signature made for another purpose (namespace), an older genuine backup served as the newest (sequence/rollback), one provider behind or lying (`heads` compares the three), two different statements with the same sequence (equivocation), a missing link (chain), a smuggled option or second key in the trusted-key text (strict single-line check).

## Where each piece lives (Bitwarden-compatible; I did not touch Bitwarden)
| Piece | Secret? | Where it should live | Loss means |
|---|---|---|---|
| Signing **public** key + newest known sequence/head (the kit) | no | a password-manager secure note **and** a printout; also fine in the repository | you can no longer prove authenticity; restores become "trust the bucket" |
| age **recipient** (public) | no | the kit | none, it is public |
| age **identity** (private) | **yes** | password manager as an attachment **and** one offline copy, never both in the same place as the kit's printout | **the backups cannot be decrypted: permanent data loss** |
| Signing **private** key | **yes** | password manager attachment, passphrase-protected; also on the Mac if backups are signed automatically (decision below) | new backups cannot be signed with the same identity; old ones still verify. Rotating means a new key, a new kit and a note in the chain |
| Bucket credentials | yes | the Keychain / password manager; recreate if lost | you create new keys; no data is lost |
The kit is generated by `node gateway/tools/backup_kit.mjs --public-key "ssh-ed25519 …" --age-recipient age1… --head-dir <newest backup>`; it **refuses** any input that looks like a private key or an age secret, and its text contains none.

## One-time setup (owner; I will not do these)
1. `ssh-keygen -t ed25519 -C macguard-backup-signing -f <path>` with a passphrase; store the private file; copy the one-line `.pub` into the kit.
2. Decide where the signing key lives for automatic signing (see decisions).
3. Create the age identity copy in the password manager (the identity already exists; its Keychain item name could not be resolved without a broad search, which was not done).

## Per backup
```
node gateway/tools/backup_anchor.mjs sign   --dir ~/macguard-backups/gateway/<stamp> --signing-key <key> --previous ~/macguard-backups/gateway/<previous stamp>
node gateway/tools/backup_objstore.mjs sync --apply     # the statement travels with the backup (owner authorises the first remote write)
node gateway/tools/backup_objstore.mjs heads --stamp <stamp> --trust-key "<public key>" --min-sequence <newest you know>
node gateway/tools/backup_kit.mjs …                    # refresh the kit with the new sequence and head
```
## After losing the Mac (clean machine, nothing from the repository)
Download the five files of the newest stamp from any destination, then `sh recover_verify.sh DIR "<public key from the kit>" <sequence from the kit> <age identity file> restored.sql`. It prints `ANCHORED OK …` and `DECRYPTED OK …` or refuses with the reason; it needs only `ssh-keygen`, `age`, a SHA-256 tool and `python3`, and it prints no secret. Load the result into a **new staging database first**.

## Adversarial cases and the test that holds each
| Case | Test | Result |
|---|---|---|
| forged self-consistent backup (attacker's own key); a genuine signature glued onto fake files | `backup_anchor` 2; `objstore` anchored 2; `recovery` 2 | rejected |
| altered manifest / checksums / ciphertext / statement | `backup_anchor` 3; `recovery` 2 | rejected, naming the file |
| signature for another namespace | `backup_anchor` 4 | rejected |
| rollback to an older genuine backup; a provider serving an older head | `backup_anchor` 5; `objstore` anchored 2 and heads | rejected / reported stale |
| equivocation; a missing or re-ordered link | `backup_anchor` 6, 8 | reported |
| loss of one provider; loss of all but one; **loss of the original machine** | `backup_anchor` 1, 7; `objstore` anchored 1, heads | the survivors still authenticate with only the public key |
| smuggled key options / second principal | `backup_anchor` 9; `recovery` 2 | rejected |
| mutation checks | file hashes not compared, rollback not checked, wrong namespace, signature check removed from the shell verifier | each makes tests fail |

## What it does not do
* It does not protect against a **compromised Mac that holds the signing key**: it can sign a bad backup. It protects against bucket-side forgery, provider rollback and the loss of the Mac.
* It does not recover the data if the **age identity** is lost.
* The statement authenticates the backup's bytes; it says nothing about whether the database content was healthy (that is `verifyRestore`).
* Rollback detection is only as good as the newest sequence you recorded: refresh the kit after each backup.

## Addendum: the external checkpoint (every provider serving an old copy)
The anchor proves a backup is genuine and consistent. It cannot show that the backup is the **newest**: if all three providers serve an old, genuinely signed sequence, every check inside the buckets passes. The answer is a statement kept **outside** them: `CHECKPOINT.json` + `.sig`, "the newest backup I confirmed is sequence N, stamp S, head H", signed by the same key under its **own** namespace (`macguard-backup-checkpoint/1`), so a backup signature can never pass as a checkpoint nor the reverse (both directions are tested).
* Make one after each confirmed backup: `backup_anchor.mjs checkpoint --dir <stamp dir> --signing-key <key> --out <new dir>` (never overwrites). Keep **several copies** where an attacker of the buckets cannot reach: the repository (it is public data: a sequence and two hashes), a password-manager note, a printout.
* Use it: `heads --checkpoint-dir d1,d2 …`, `drill --checkpoint-dir …`, `recover_verify.sh` with `MG_CHECKPOINT_DIRS=d1:d2`, and `backup_preflight.mjs --checkpoint-dir …`. A copy older than the checkpoint is `rollback or loss`; the same sequence with another head is a `fork`; two authentic checkpoints that disagree are `equivocation`; a newer copy is accepted (the checkpoint is merely behind).
* Tests (`backup_checkpoint.test.js`, 8, plus one drill test in `objstore.test.js`): all three providers serving sequence 2 while sequence 3 was confirmed is **caught with the checkpoint and looks healthy without it**; one provider holding the confirmed head is current and the others are reported behind; a forged checkpoint, a checkpoint signed for another purpose and a backup signature reused as a checkpoint are refused; replacing one external copy with an older authentic one does not lower the bar (the newest authentic copy counts); an old checkpoint is flagged `stale`; five mutations of the code each make tests fail.
* **Residual risk, stated:** if **every** external copy is old, nothing can tell. That is why several copies in different places are kept and refreshed after each backup. A checkpoint tells you the newest sequence you *confirmed*; a backup you never confirmed is not covered.
