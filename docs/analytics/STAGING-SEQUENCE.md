# Staging release sequence (prepared; NOT executed anywhere)

Generated by `gateway/tools/staging_sequence.mjs --markdown` and drift-tested: edit the tool, not this file. Order: **backup → D1 migrations → deploy → smoke → security → rollback**, rehearsed on a separate staging Worker and database first. Staging has no Custom Domain, no route, no R2 and no cron, so it touches no DNS, no production hostname and no production data.

Scope legend: `local` runs on this machine only; `remote-read` reads from Cloudflare/HTTP without changing anything; `remote-write (staging only)` changes the staging resources and needs the owner's go-ahead for staging; `remote-write (production)` needs a separate go-ahead for each command.

## Invariants checked by `--check` and by `test/staging.test.js`

- staging Worker name differs from production
- staging database name differs from production and ends in -staging
- staging never reuses the production database id
- staging has no route and no Custom Domain (no DNS is touched)
- staging has no R2 binding (never reads the private Premium bucket)
- staging has no cron trigger (does not spend the production collector's GitHub allowance)
- staging holds no secret-shaped value
- every remote-write step before P1 is scoped to staging
- no staging step names the production database as a target
- every step has a verification and a rollback statement

## What this does not prove
A staging pass proves the code, the migrations and the restore path on real D1 and real workerd. It does not prove the production edge (Custom Domain TLS, WAF), the production secrets, the GitHub collector from production egress addresses, or any GuardOps receiver. Those stay marked UNKNOWN until observed in the environment itself.
