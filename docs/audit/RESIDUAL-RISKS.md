# Residual risks (open after the final audit)

"Blocking" means it prevents a GO under the criteria of the audit brief. Owners are roles, not people.

| ID | Risk | Why it remains | Blocking | What closes it |
|---|---|---|---|---|
| RR-01 | Repository controls: secret scanning, push protection and Dependabot security updates are off; `main` accepts direct pushes with no required checks or reviews; immutable releases are off (FA-28) | They are repository security settings; changing them is a human decision, and the log bot pushes to `main` so a pull-request-only rule needs a deliberate bypass for it | **yes** | owner enables the three scanners, an immutable-releases setting and a ruleset (required status checks, bypass only for the log bot), then `gh api` output is attached to the readiness report |
| RR-02 | No independent attestation of the review (in-toto/SLSA, signed by the *review* job). `manifest.evidence` is the *publishing* workflow's statement (FA-11) | A new signed statement and verifier support would be a feature, not a defect fix | no (documented in `limits`) | add `actions/attest` for the candidate artifact and verify it in `verify_release.py` |
| RR-03 | The private quarantine service is not deployed; real OAuth, OIDC, D1 limits, rate limits and the panel UI were not exercised (FA-29). Audit rows are append-only only against the service itself | Needs Cloudflare Workers/D1 credentials and a GitHub OAuth app | **yes** (the brief requires real authorization in the private API) | deploy to a staging Worker, run the adversarial suite against it (`evidence/audit-quarantine-service.md` lists it), then production; add Cloudflare rate-limiting rules for `/auth/*` and `/api/decisions` |
| RR-04 | No scheduled run has been observed (FA-30) | The repository is one day old; first cron `03:17 UTC` | **yes** (proof of autonomous operation) | read `gh run list -w "Daily source review" --event schedule` after 2026-10-19 03:17 UTC, then `publish`/`site` follow-ups; no human action |
| RR-05 | Public verification runs after GitHub Pages is deployed; a bad deploy would be live until the next run (the pre-deploy gates are `verify_release` and `docs-check`) | A two-phase Pages deploy would be a new mechanism | no | accepted |
| RR-06 | Linux gate uses Ubuntu YARA 4.5.0, shipped engine is 4.5.8; the macOS job measures 4.5.8 but is a VM, not an independent macOS machine | hosted runners cannot nest virtualization | no | self-hosted Mac (human) |
| RR-07 | The browser offers two copies of the package to check (site copy vs GitHub release) and the verifier's hash is served from the same origin as the verifier | Product/trust-presentation decision | no | sign the verifier in `publish.yml` and link its signature; point the button and the link at one copy |
| RR-08 | GitHub Pages cannot send headers; the CSP there travels in `<meta>` (no `frame-ancestors`, no HSTS control, `access-control-allow-origin: *` by platform) | platform limit | no | Cloudflare is the host that gets real headers; a custom domain in front of GitHub Pages would be needed for parity |
